# Публикация и проверка

Модуль публикации оборачивает git-операции над двумя репозиториями (контент-репозиторий + репозиторий темы). Репозитории **не блокируют друг друга** и возвращают независимые `RepoPublishResult`.

## GET /api/publish/preview

Данные первого экрана страницы публикации: детали изменений обоих репозиториев, автосгенерированные сообщения коммита, недавние коммиты и состояние. Без параметров.

**Возвращаемое значение** `PublishPreview`, ключевые поля:

| Поле | Описание |
|------|------|
| `branch` / `ahead` / `behind` | Ветка контент-репозитория, опережение/отставание (локально закэшированные значения) |
| `changes` / `files` | Детали изменений контент-репозитория `{ path, state: "new" \| "modified" }[]` и список файлов |
| `message` | Автоматическое сообщение коммита контент-репозитория |
| `themeChanges` / `themeFiles` / `themeMessage` / `themeStatus` / `themeRecent` | Соответствующие сведения репозитория темы (`themeStatus` равен `null`, когда не подключен) |
| `themeDepsInstalled` | Установлены ли зависимости темы (определяет возможность локальной проверки) |
| `recent` | Последние 20 коммитов контент-репозитория `{ hash, date, subject }` |

```bash
curl http://127.0.0.1:5175/api/publish/preview
```

## POST /api/publish/probe

Лёгкое сравнение с удалённым репозиторием: `git ls-remote` сверяет tip ветки, **не скачивая ни кода, ни объектов**.

| Поле body | Тип | Обязателен | Описание |
|-----------|------|------|------|
| `repo` | `"content" \| "theme"` | да | Какой репозиторий замеряется |

**Возвращаемое значение** `RemoteProbe`: `{ behind: number | null }` — `0` совпадает с удалённым; `>0` точное число отставания; `null` удалённый ушёл вперёд, но величина неизвестна (выяснится после pull).

```bash
curl -X POST http://127.0.0.1:5175/api/publish/probe \
  -H "Content-Type: application/json" -d '{"repo":"content"}'
```

## POST /api/publish

Публикация одним кликом. Поток: контент-репозиторий (**проверка → add -A → commit → pull --rebase --autostash → push**; провал проверки блокирует этот репозиторий) + репозиторий темы (commit → push, без локальной проверки).

| Поле body | Тип | Обязателен | Описание |
|-----------|------|------|------|
| `contentMessage` | `string` | нет | Сообщение коммита контент-репозитория; **пустое генерируется автоматически** (формат `type(scope): ≤30 знаков`) |
| `themeMessage` | `string` | нет | Сообщение коммита репозитория темы; аналогично |

**Возвращаемое значение** `PublishResult`:

```json
{
  "ok": true,
  "content": { "ok": true, "hadChanges": true, "commitHash": "a1b2c3d", "pushed": true, "log": ["..."] },
  "theme":  { "ok": true, "hadChanges": false, "pushed": false, "log": ["无变更，跳过"] }
}
```

`RepoPublishResult` одного репозитория: `ok` (общий успех этого репозитория), `hadChanges`, `commitHash?`, `pushed`, `validationOutput?` (полный лог при провале проверки контент-репозитория), `log[]` (пошаговый журнал). Верхнеуровневый `ok = content.ok && theme.ok`.

```bash
curl -X POST http://127.0.0.1:5175/api/publish \
  -H "Content-Type: application/json" -d '{}'
```

> [!WARNING]
> Это интерфейс, который реально создаёт git-коммиты и выполняет push. Перед вызовом рекомендуется прогнать `preview` и убедиться в масштабе изменений; при провале проверки контент-репозитория коммитов не будет вовсе.

## POST /api/validate

Отдельно выполняет предпубликационную проверку: запускает в репозитории темы `scripts/content/sync.mjs --dry-run` (окружение с `CONTENT_DIR`, таймаут 180 секунд, вывод обрезается до 4000 символов). **Предпроверка чисто в памяти: ничего не пишет на диск и не создаёт изменений**.

**Возвращаемое значение** `{ ok: boolean, output: string }` — `output` это вывод валидатора (формат YAML, опечатки в полях, локализация проблем схемы frontmatter).

```bash
curl -X POST http://127.0.0.1:5175/api/validate
```
